# Finish the connected workspace

1. In the same Google Cloud project as Life OS Web, enable the Google Sheets API. In Life OS Settings → Connections, use Connect read-only spreadsheet. Calendar list/events read permissions remain required. Review the Career and Academic import previews before applying. They copy source records, not active tasks. Source-reported grades remain unverified until checked; partial grade averages are not final grades. Promote only current, confirmed goals/projects.
2. Planner → Scheduling preview (or Settings → Connections): grant separate-calendar permission, then create Life OS calendar. The new scope is `https://www.googleapis.com/auth/calendar.app.created`; broad `calendar.events` write scope is not requested. Generate a fresh preview, review every proposed session and reserve. Test one future synthetic task, confirm it in Google, then Undo. Never use an existing personal/academic calendar as the write destination.
3. Settings → Privacy & account: enroll a TOTP authenticator if desired, save the setup securely, verify the code, then check sign-out/sign-in. Never test account deletion on the real account. Supabase project administrators can remove a lost MFA factor only after independently verifying account ownership; app password recovery intentionally does not bypass verified MFA.
4. Password recovery needs the exact HTTPS `/auth/recovery` path in Supabase Auth redirect allowlist and working Auth email delivery. Test receipt and the single-use expired-link behavior. No SMTP subscription was purchased. Sender defaults and provider limits may require project-owner configuration.
5. iPad Safari → Share → Add to Home Screen. Open that icon, sign in, then Updates → Enable push on this device. Enable Push for the desired category and send a test outside its quiet hours. Notifications use Vancouver time, with default 22:00–08:00 quiet hours. Delivery is best effort. Normal notifications show only a generic private-workspace summary on the lock screen.

## Operator notes

- Daily read-only calendar refresh remains the existing Vercel 13:00 UTC job. The separate Supabase `lifeos-notifications` job invokes only `/api/internal/notifications` every 15 minutes. It does not schedule tasks or sync Google every 15 minutes.
- Notification worker credential is distinct from CRON_SECRET and stored as sensitive Vercel environment configuration and Supabase Vault. Install its timer only after the deployed worker responds successfully; use the narrowly authenticated `/api/internal/notifications/setup`. Never place secrets in migrations, query text, Git or support screenshots.
- Device endpoint/auth keys are service-only and omitted from user exports. Service worker handles push/click only; never cache authenticated pages/API data.
- A failed or ambiguous reservation is kept as a durable job. Review Recent reservation runs → Undo. External edits, uncertain provider etags and sessions within the freeze window are preserved. An uncertain event may need removal directly from the dedicated Google calendar, then Undo again to reconcile. Do not delete unrelated events. An ambiguous calendar creation needs operator reconciliation using its durable job/provider calendar list; do not clear the intent and blindly create again.
- Google OAuth External Testing commonly gives seven-day refresh tokens for these scopes. Review publishing status for a lasting personal connection. Publishing is not the same as Google verification and must not be claimed as verified.
- Supabase RLS checks the actual Auth session record and requires aal2 whenever a verified MFA factor exists. Administrative service-role operations remain server-only. No client-editable metadata grants authority.
- Account deletion is a separate explicit password-confirmed DELETE action with a seven-day cancellation period. Daily worker claims the request, verifies the allowed owner identity, revokes Google authorization, then deletes the Auth user/cascading Life OS data. Source Google calendars and spreadsheet remain intact. Deletion cooldowns, cancellation and cascade behavior are tested only with synthetic accounts.
- Full hosted backup/restore remains deferred. User export restoration tests do not establish full hosted disaster recovery readiness.
